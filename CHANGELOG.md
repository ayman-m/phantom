# Changelog

All notable changes to Phantom are documented here.

The format is loosely based on [Keep a Changelog](https://keepachangelog.com/en/1.1.0/), and this project adheres to [Semantic Versioning](https://semver.org/spec/v2.0.0.html).

Each release section is written in operator language, not git-shortlog language. For commit-level granularity, run `git log`.

---

## [v1.0.5] — Unreleased — *Model providers: Claude and OpenAI beside Vertex, with a live model registry and one default model*

Phantom can now run on Anthropic Claude and OpenAI as well as Google Gemini. Add an API key on `/providers`, pick a model on `/models`, and chat, jobs, subagents and the benchmark all use it. Vertex is no longer required.

**Added.**

- **Claude and OpenAI as model providers.** `/providers` gains an **Anthropic (Claude API)** card (API key, optional base URL) and an **OpenAI (Responses API)** card (API key, optional organization, project and base URL). Each has **Test Connection**, which lists the models the key can see without spending tokens. Calls go straight to the vendor's API over HTTPS with the key from the ProviderStore; Claude and OpenAI keys have no environment-variable fallback. OpenAI calls ask that nothing be stored on the OpenAI side. A saved key is only ever sent to the base URL it was saved with, so changing a base URL means typing the key again; a base URL must be `https` and may not point at this install, at `localhost` or a loopback or link-local address, or at an internal host name (private-network gateways are allowed); chat, subagents, `/compress`, `/plan` and compaction enforce the same rules as the Providers page and Test Connection). The new test routes sit under the credential prefix, so API keys get 403 on them like on the rest of `/api/agent/providers`.
- **A live model registry.** `/models` and `GET /api/agent/models` serve one list per provider: Phantom's built-in catalog (prices, thinking behaviour, the recommended model) merged with the provider's own live model list. The live list is cached for ten minutes and served stale while it refreshes in the background, and the last good list survives a provider outage for a day. Each model shows an availability badge (Deprecated, Unverified, Unpriced, Not visible to key, Not configured; retired models are hidden), its price and the date the price was checked. Vertex has no model list, so Gemini models get a **Verify** action on their detail page that asks Google whether the model is enabled (a token count, no generation).
- **One default model.** The install default is the settings key `defaultModel`, a `provider/model` ref, set with **Set as default** on `/models`. It replaces the `geminiModel` setting (an existing override is renamed on first start) and the `GEMINI_MODEL` environment variable (removed). A turn resolves its model from the chat header, then the session's `/model` preference, then the default. If no default is set, or it names a provider with no credentials (a fresh Claude-only install starts with a Gemini default), the recommended model of the first configured provider serves and `/models` marks it **Default (derived)**.
- **Bad models fail loudly.** A model that is unknown, retired, ambiguous, not selectable or on an unconfigured provider ends the turn with a `MODEL_UNAVAILABLE` error that says why and lists models that would work, and writes a `chat_model_rejected` audit row. Nothing is silently swapped for another model. Jobs, the benchmark and `/model` use the same check where a model is saved: the settings and jobs endpoints answer 400 with suggestions, and models are stored as `provider/model`. A bare model name still works when exactly one configured provider offers it.
- **Cost for every provider.** Cost rows now carry the provider, the model ref, cache-write and reasoning tokens and a priced flag. `/observability/cost` groups by Provider, Model (`provider/model`), Call kind, Session or Job and gains an **Unpriced calls** card; the **Total cost** card says *unpriced* when no call in the window had a price. A call to a model with no known price is counted and named, never billed at $0 or at a neighbour's rate. `/cost` in chat breaks today down by provider and model and names unpriced calls. The **Cost warn over budget** hook reads the same rows, so its daily total includes every provider (and is a floor when some calls were unpriced). Benchmark case costs are real now; earlier runs read $0 because the runner looked in the wrong field. A benchmark case on a model with no known price stores a null cost and shows *unpriced* on the run, list and compare pages instead of $0.0000, and it is left out of the run's cost p50 and p95 (a run with no priced case has no percentile). Gemini thinking tokens are billed as output (Google reports them apart from the answer tokens, and earlier versions left them out, so thinking-heavy turns on Gemini now cost more than they used to show).
- **Provider activity in the audit log.** New audit actions: `provider_models_refreshed` and `provider_models_refresh_failed` (live list fetches), `provider_test` (every Test Connection: provider, outcome and HTTP status, never the key), `chat_model_rejected` and `provider_event` (an adapter had to change a setting, dropped a malformed tool call, or the model declined to answer; also sent to the Wire events panel). `/observability/events` gets filter chips **Model list refreshes**, **Failed model list refreshes**, **Model rejected**, **Provider tests**, **Provider notes** and **Turn costs**.
- **Five journeys.** *Add Claude as a model provider with an API key*, *Add OpenAI as a model provider with an API key*, *Choose the install's default model*, *Switch to another provider's model in the middle of a session* and *See what each provider and model costs, and find unpriced calls*. *Read your token + USD spend with /cost* and the model, job and benchmark journeys are updated.

**Changed.**

- **Vertex is optional.** The bundle manifest no longer marks the Vertex provider required, and `health_status` no longer reports `ok: false` just because there is no Vertex provider. Memory and knowledge-base search still need Vertex embeddings: on an install without Vertex they use the offline hash-similarity stand-in, which `health_status` reports as `embedder_mode: stub` with a warning (a limit, not a fault). The agent's system prompt now describes both modes instead of promising Vertex embeddings.
- **The agent no longer sees an OpenAI organization, project or base URL.** `providers_list` and `providers_get` return Vertex's project and region as before, but report every other provider setting only as set or not set (`config_set`), so an id or an internal gateway host does not end up in a chat transcript. Read the values on `/providers`.
- **Stored history is provider-neutral**, so a session can change provider between turns; earlier messages are replayed as plain text to the new model. Tool names are encoded per provider (Claude and OpenAI do not allow dots or long names) and mapped back, so approvals, hooks and audit rows still see the same tool names.
- **Closing the browser cancels the model call.** A chat turn, a subagent, `/compress`, `/plan` and automatic compaction now stop their in-flight request to Gemini, Claude or OpenAI when the connection drops, instead of running to the end and billing for an answer nobody reads. A cancelled turn writes no failure audit row and no error event; a cancelled subagent task is marked *aborted*. This applies to scheduled jobs and benchmark cases too: they call the chat endpoint over HTTP, so a job or case whose caller gives up (the scheduler's 5-minute read timeout, an operator stopping the run) now stops the model call instead of letting it finish unseen.
- **The `model` event** in Live telemetry now carries the provider and the `provider/model` ref beside the model name.
- **`thinking`** (the job and benchmark toggle) maps to each provider's own reasoning mode instead of Gemini's thinking settings only.
- **The unused `modelRequirements` block is removed from the bundle manifest.** Nothing ever read it.

**Removed. Check before upgrading.**

- **`GEMINI_MODEL` is gone.** Pick the default on `/models` (**Set as default**) instead; if you had set the variable, remove it from your `.env`.
- **`ANTHROPIC_API_KEY` is no longer read from the environment.** A Claude key must be saved on the Anthropic card of `/providers`. A stored `geminiModel` setting is renamed to `defaultModel` on first start, but only when its value is a model the catalog serves (`gemini-3.8-flash`, `gemini-3.7-flash`, `gemini-3.5-flash`, `gemini-3.1-pro-preview`, `gemini-3.0-pro`, `gemini-2.5-pro`, `gemini-2.5-flash`, `gemini-2.5-flash-lite`). Any other value (a typo, a retired or private id) is dropped instead of being carried over, because it would fail every turn with `MODEL_UNKNOWN`; the default then stays at `vertex/gemini-3.1-pro-preview`, the MCP log carries a warning, and the audit log has a `settings_changed` row from `migration` that shows the discarded value. If chat suddenly runs a different model than before the upgrade, check that row and re-pick on `/models`.
- **The MCP's `GET /api/v1/models` is removed**; nothing in the UI used it. `GET /api/agent/models` is the model list.
- **Sessions and jobs pinned to a Gemini 2.5 model** keep working while that model is still served; once a model is retired they fail with `MODEL_UNAVAILABLE` rather than being moved to another model, so re-pick one on `/models`.

**Known limits.**

- `/compress`, `/plan` and automatic compaction use the session's model but write no cost row, so their spend is not on the cost page or in `/cost`. A subagent's calls are recorded under the subagent's own session and are not added to the parent turn's cost line.
- Embeddings (memory and knowledge-base search) are Vertex-only; there is no OpenAI or Claude embedding path.
- `GEMINI_API_KEY` is still read from the environment only; it has no card on `/providers`.
- There is no automatic fallback when the provider serving a turn is down: the turn fails and you pick another model.
- The Claude and OpenAI adapters were verified against recorded responses and request-mapping tests, not yet against the live vendor APIs.

**Documentation.** Review `/help/architecture#model-providers` (new; it also answers the old anchors `#model-resolution` and `#provider-store`, which are now sub-sections of it) and `/help/user#models-providers` (rewritten). Rewritten around the new cost rows: architecture `#cost-tracking` and user guide `#cost-ux`. One- or two-line corrections where the old text had become false: architecture `#chat-lifecycle` (including `#model-routing`), `#tool-dispatch`, `#compaction`, `#vertex-cache`, `#plan-mode`, `#subagents`, `#setup-wiring` (provider cards, test routes, embedder note), `#jobs-subsystem`, `#benchmark-harness`, `#observability-overview`, `#secret-store`; user guide `#chat`, `#agents-ux`, `#memory`, `#jobs`, `#obs-bench`, `#settings-precedence`. The chat-lifecycle sections no longer name the removed `callGemini` functions. The API reference (`/help/api`) covers the new test routes, the Providers page save, the model registry fields and `model_id` on jobs and benchmark runs.

## [v1.0.4] — Unreleased — *Hook, benchmark and status fixes, and documentation coverage*

A patch release from a second page-by-page walkthrough: the pages the first one did not reach (Services, Hooks, Benchmark and the About and Observability pages) now have fixes and documentation.

**Fixed.**

- **Caldera shows its real status on Services.** The health check looked Caldera up under a setting that never existed, so Caldera always showed as unknown on `/settings` (and in the pipeline view) even when it was up. It now checks the address in `CALDERA_URL`, which the compose file already sets (default `http://caldera:8888`), so Caldera reports healthy or unreachable like the other services.
- **Benchmark runs work.** Every case of a benchmark run failed with a 401 because the runner called the chat endpoint without credentials. It now authenticates the same way scheduled jobs do, so runs score real results.
- **A built-in hook can only be saved on an event it supports.** The form previously accepted, for example, the Cost warn over budget hook on the user-prompt event, where it could never do its job. It now refuses the combination and says which events the built-in runs on.
- **The cost and context warnings from the built-in hooks now reach `/notifications`.** The Cost warn over budget hook (RunEnd) and the Pre-compact context warning hook (PreCompact) fired and left their `hook_dispatched` audit rows, but the notification they publish was rejected because its topic was not declared in the manifest, so the operator never saw a warning. The topics `cost-warning` and `context-warning` (warning severity) are now declared, and the warnings show in the Alerts tab with a warning icon, the title and the details.
  - **The notification category setting is gone.** Each built-in publishes to one fixed topic; a free-text category could only ever name an undeclared topic. Hooks saved earlier keep working: the old `notify_category` value is ignored.
  - **A failed publish is no longer silent.** The agent logs it as an error with the MCP's status and message, and the chat turn is not interrupted.
  - **The cost threshold helper is clearer.** Setting **Daily cost threshold (USD)** to 0 means no threshold: the warning fires on the first turn of each repeat window whatever the spend.
- **Backups now include your hooks.** `hooks.json` joins the backup zip (disabled hooks too) and restore puts them back under their original ids, after operator state and before jobs. A hook whose id already exists on the destination is kept and counted as skipped; Overwrite replaces it. If the destination's hooks cannot be listed, restore skips the section rather than writing blind.
  - **Secrets are left out.** Literal values in a command hook's `env`, an HTTP hook's `headers`, and a built-in's secret fields are not written to the zip; `secret:ENV_NAME` references are kept. A hook that lost a value is restored **disabled**, with a warning naming the fields, and never replaces an existing destination hook. A hook's URL and a command hook's text are kept as written, so treat the zip as sensitive.
  - **Log destinations are still not in the backup**; recreate them by hand after a restore.
- **The Claude Code CLI integration is removed.** Phantom no longer runs the Claude Code binary: the hidden chat route, the CLI token field on `/providers`, the stored CLI token slot, the unused `@anthropic-ai/sdk` package and the CLI install in the agent image are gone. It could not be used in line with Anthropic's terms, and it started a process that inherited the container's environment. The Anthropic card on `/providers` keeps the API key field; calling Claude through the API is planned for a later release. A CLI token saved earlier is ignored.
- **The Personality page shows only what is used.** Permission Level, Default Model, Fallback Model, Max Concurrent Runs, Daily Summary, Summary Time and Escalation Threshold were stored but nothing read them, so they are removed along with the "Spark" wording. The page now holds the `Personality.md` editor and the action policy. Personality saved by an earlier release still loads; the unused keys drop out on the next save.
  - **The Tuning panel is gone too.** Its four knobs (Vertex cache, auto-compact minimum, MMR and temporal-decay lambdas) were never read; the fixed defaults still apply.
  - **One home for the defaults.** The page now loads the default persona and action policy from the server (`GET /api/agent/personality/defaults`), so Reset Defaults and `personality_reset` agree, and the default policy treats `http-sender` and `wec-sender` as external. Existing installs keep their stored policy until Reset Defaults.

**Documentation.**

- **User guide (`/help/user`).** New sections: **Benchmark Runs** (`#obs-bench`: running a benchmark, the run list and detail pages, comparing two runs), **Runtime Events** (`#obs-runtime-events`) and **What's New & Release History** (`#about-releases`: the About menu, `/about/whats-new`, `/about/history`). The **Knowledge Bases** section (`#knowledge`) now explains browsing a knowledge base: the Entries tab, Try search, and the fact that there are no Import or Settings tabs. The upgrade section no longer says the About dialog lists image digests; it shows the running version, and the digests are on `/observability/connectors`.
- **Architecture page (`/help/architecture`).** New sections **Benchmark Harness** (`#benchmark-harness`: manifest and scoring, storage in `benchmark_runs.db`, the wires between browser, agent, MCP and chat route, the `/api/agent/bench` endpoints, and the known gaps) and **About & Release Notes** (`#about-release-notes`: `lib/release-notes.ts` as the single source for the About dialog, `/about/whats-new` and `/about/history`).
- **Journeys.** New journey **Read the observability overview page** (`observability-overview-landing`). **Run the phantom-soc-v1 benchmark and compare runs** (`bench-run-benchmark`) now covers the compare page: the shareable `?base=&head=` address, the 10% green and red rule, the FIXED / REGRESSED labels and the two extra API calls.

## [v1.0.3] — 2026-10-12 — *Session lifetime, walkthrough fixes and corrected help pages*

A patch release by operator decision: one new setting, plus the fixes from a page-by-page walkthrough of v1.0.2 (jobs, chat, notifications, tasks, settings, skills) and an audit of the help pages and journey catalog against what the product actually does.

**Added.**

- **You can choose how long a sign-in lasts.** The UI session was fixed at 2 hours, which signed you out in the middle of long working sessions. The new **Session lifetime** card on `/profile`, under Change password, lets you pick 1, 2, 4, 8, 10, 12 or 24 hours (the API accepts any whole hour from 1 to 24). Installs that never touch it behave exactly as before: 2 hours.
  - **Same safeguards as changing your password.** Saving needs a signed-in session and your current password, so someone holding only your browser cookie cannot extend future sessions. Wrong passwords on this card count against the same lockout as Change password (five in a minute, then 60 seconds).
  - **When it applies.** To sign-ins after the change. Sessions that are already open, including yours, keep their current expiry, and saving does not sign you out. Sign out and back in to get the new length.
  - **One place for the value.** It lives in the agent's auth database (`auth_sessions.db`) next to the sessions themselves, not in an environment variable. The login cookie's lifetime is derived from the expiry the server returns, instead of a second hard-coded 2-hour constant in the web app, so the cookie and the server can no longer disagree.
  - **Not reachable by the agent or API keys.** It is a UI-only security setting: no chat tool reads or writes it, the settings tools do not list it, the agent refuses to change it and points you to the card, and API keys and the internal token are refused with 403.
  - **Audited.** Each change writes `session_lifetime_changed` (old and new hours, never a secret) to `/observability/events`; a wrong password writes `session_lifetime_change_rejected`.
  - **Honest failures.** If the MCP is unreachable or the bearer gate fails, the card reports a service problem (503) rather than "incorrect password", and that does not count toward the lockout.
- **A job's Description is saved.** The Description box on `/jobs/new` was accepted and then dropped. It is now stored with the job, shown under the schedule on the `/jobs` list and under the title on the job page, copied by Duplicate, written to the job's YAML mirror when set, and accepted by the agent's `jobs_create` / `jobs_update` tools. Existing jobs read as having no description.
- **`/tasks` lists running log generators.** The xlog data workers now appear with a Stop button (and the `/tasks` chat command lists them). An explicit stop removes the worker from xlog and from the list; a generator that finishes on its own stays listed as Stopped.
- **In-app dialogs replace browser pop-ups.** Renaming a chat session is now an inline field in the sidebar row (Enter or clicking away saves, Esc cancels, a blank or unchanged name is ignored). Deleting a session, stopping a worker, aborting a task, uninstalling a plugin and the other destructive actions open a themed confirmation dialog, and errors show as toasts. Esc closes only the dialog. Nothing freezes the page any more.
- **Journey catalog: audited, 151 journeys.** Every journey was checked against v1.0.2: stale labels, tools and pages fixed, 3 retired and 29 added. 16 of them are **outcome journeys** that take an analytics skill or attack scenario from the prompt through to verifying the result.

**Changed.**

- **Chat forks nest under their parent.** The sidebar showed every fork as a top-level session. A fork now appears indented under the session it was forked from, at any depth.
- **The embedder follows your Vertex provider.** A fresh install boots with no Vertex provider, and the memory and knowledge embedder stayed on the offline stub until a restart even after you added Vertex on `/providers`. It is now re-selected as soon as a Vertex provider is created or updated, and the bundled knowledge base is re-indexed in the background. `health_status` reports the live mode, says what to do when it is still the stub, and says so when the provider was removed (the running embedder keeps its credentials until restart). The stale references to the removed `/setup` page in those messages are gone. If Vertex rejects the key, the previous embedder stays and `health_status` says why; once the key is fixed the knowledge base is re-indexed without a restart.
- **Documentation of the log generator's token.** The user guide, the README and the installer's final message now say where the xlog API token comes from (the `XLOG_API_KEY` line in `/opt/phantom/.env`) and where to create the instance (`/connectors`, Instances tab). The wording about a first-run setup form and the `/instances` path is gone.
- **Retired the stale first-run `/setup` documentation.** The first-run setup page and its API were removed in an earlier release, but the user guide (*Where Settings Live*), the architecture page (boot sequence and Secret Store notes), the Secret Store diagram, several journeys and the API reference still described them. They now describe the real flow: sign in as `admin` with `PHANTOM_DEFAULT_ADMIN_PASSWORD` from `/opt/phantom/.env`, change the password on `/profile`, add the Vertex credentials on `/providers` and connector instances on `/connectors`. The caldera section of the user guide now says caldera's login comes from `/opt/phantom/.env`, not from a setup form. The `setup_completed` audit action, which nothing has recorded since the setup endpoint was removed, is no longer listed.

**Fixed.**

- **Jobs.**
  - **Duplicate** now carries the whole job: prompt or tool arguments, the real schedule (Repeating, Run at or Custom), timezone, enabled flag, model, thinking and policy, under a unique `<name> (copy)`. The Create button was stuck disabled because the prompt came across empty.
  - **The model dropdown** always said "No models registered yet". The new-job form and `/models` now read the same registry.
  - **Edit** no longer wipes a job's model override, thinking flag or permission policy when you save.
  - **Paused jobs** show no next run (it used to be a frozen time sliding into the past, and resuming fired a catch-up run). A completed run-once job offers no Pause or Resume (Trigger Now, Edit and Duplicate remain); resuming one is refused until you set a new Run-at time, so a finished one-shot can no longer re-arm itself for next year. The audit row and the notification for a run report the next run that is actually stored.
- **Scheduled jobs no longer fill the load-issues list on every restart.** At boot each runtime job was re-added from its YAML mirror and reported as "already exists". Replay is now idempotent: an identical job is skipped silently, a changed definition (cron, timezone, action, run-once, description) is applied, and enabled state and run history stay as the database has them, so a paused job stays paused and a completed one-shot is never re-armed. A bad cron or malformed YAML still shows up as an issue. After the replay, each runtime job's mirror file is rewritten once if it differs from the database (an older file still saying `enabled: true` for a finished one-shot, or an old header), so mirrors match the live state; a file that failed to load is left untouched.
- **`/notifications`** shows the job name, outcome and run summary, tracks read state correctly, and clicking a card opens the job.
- **`phantom_mcp_tool_calls_total`** counted nothing; it now counts tool calls by tool and status (chat, jobs and connector batches; built-in actions that `agent_batch_propose` runs directly are counted only by the batch counters).
- **`/skills`** category counts follow the list on screen and the placeholder Invocations tile is gone. **`/knowledge`**'s detail page reports the same total as the index card and loads every page of entries; the Import and Settings tabs, which did nothing, are removed. `/providers` explains what the Anthropic API key field does.
- **`/settings` Services** reads real health from `/api/agent/health` (status, response time, last checked). It showed Unknown for every service, a hard-coded service count and uptime, and sample deploy events from another product; those and an unwired Restart button are removed.
- **Instances on `/connectors`** keep their Connected or Error badge after a page reload. The page read a key the server never sends, so every instance came back as Not Tested until you clicked Test again; it now shows the connector's last known connection state (from your last Test or from a tool call).
- **Uploaded connectors** show up on `/connectors`. The upload said to POST to an endpoint that does not exist and the grid only listed the nine bundle connectors, so an uploaded one was invisible. It now appears as an Uploaded card (tools, config fields) that you Install like any other, the button reads Upload rather than Upload & Install, and the card has a Delete connector button (refused while instances exist). An upload whose id is `install`, `installed` or `upload` is refused with a clear message: those are fixed route names, and such a card could not have been deleted.
- **`/notifications` controls work.** Mark All Read, Load more and the date dropdown did nothing, and clicking a card never marked it read (so the Unread tab never emptied). Clicking a card now marks it read, Mark All Read marks every unread row, the date dropdown filters to Today, 7 or 30 days, and Load more fetches the next 50 (a malformed `since` on the API is now a 400 instead of silently matching nothing or everything). The settings gear, which had no settings behind it, is removed. The help pages and journey no longer describe an audit-log view with a `notification_reads` table; notifications are rows in their own store.
- **`/skills` shows only what is real.** The page carried a built-in list that still named skills that no longer ship (such as `generate_shared_iocs`) and appeared whenever the live list failed to load; it now has no list of its own, and shows a loading, retry or empty state instead. Removed the per-skill on/off switch and the Active tile (they changed the page view only; every skill is always available to the agent), the 24h, 7d and 30d call counts, the "1 agents" figure, and the Max Concurrent Agents, Eligible Agents and Loading Mode controls, none of which the agent reads. The detail panel now lists the skill's real properties, and its Save Changes button saves.
- **`/providers`** no longer shows OpenAI and Ollama cards with roadmap wording. Neither has a backend, so the cards (disabled fields and buttons) are removed; the Models page empty states no longer tell you to add OpenAI credentials.
- **Tool names the UI mentions are real.** The table that decides which tool calls get a red or amber approval border (and carries the read-only and parallel-safe flags) listed 25 tools that no connector provides (for example `xsiam_execute_xql_query`, `caldera_start_operation`, `xlog_create_worker`), so the real ones (`xsiam_run_xql_query`, `caldera_create_operation`, `phantom_create_data_worker`) never matched and fell back to the plain default; it now names the real tools, under both their flat and `<connector>.<tool>` names. The placeholders on `/jobs/new`, the hook examples and the Slack approval hook's default matcher use real names too, and a test fails if one stops matching a tool. The chat's per-turn cache of settings, skill and marketplace reads also clears after a `settings_update`, `settings_reset`, skill edit or data-source install now; it matched names that do not exist.
- **A job's "Require approval" list is gone.** The field on `/jobs/new` (and the `require_approval` key of a job's permission policy) was saved and then never acted on, so it promised approval cards that never appeared. Whether a tool call needs an approval card follows the install's approval list only; a job's policy keeps its Allowed tools and Denied tools lists. One side effect: a tool that a job listed under Require approval but left out of a non-empty Allowed tools list is now blocked by that allow list, where before it ran (the chat route only acted on a deny, and the Require approval match came first). The Personality page no longer says local tools are always gated by an approval card.
- **Restore no longer writes blind.** When the destination's existing instances, skills, data sources, workflow state or jobs could not be listed (the MCP was down or answered an error), restore treated the destination as empty and tried to write the whole section over entries that were already there. Without Overwrite it now skips that section and says so under Warnings; with Overwrite it writes anyway, as you asked.
- **Backups include your workflow state.** The journeys you marked tested and your saved metric bookmarks (kept in `operator_state.db`) were missing from the backup zip, so a restore onto a new install started them over. The zip now carries them as `operator_state.json` and restore writes them back, keeping a key the destination already has unless you tick Overwrite. The user guide no longer lists log destinations among the backup contents: they are not in the zip.
- **Asking the agent which model it is** no longer changes the global default model. The turn's model is given to the agent as read-only context, and `settings_update` / `settings_reset` refuse model-selection keys (those are operator/REST-only).
- **The agent names skills that exist.** Its system prompt listed skills that no longer ship; it now names the shipped ones by path, and a test fails if one goes missing.
- **`load_simulation_skills` no longer returns nothing** for a sensible combination of filters. Skills that declare no attack type or complexity are no longer excluded by those filters, keywords match name, description and body, keywords are never dropped (no match returns an empty list and a `hint` pointing at `skills_read`), and when metadata filters match nothing only the smallest set of filters that actually restores matches is dropped and reported in `filters_relaxed`; relaxed results are capped at 10 and carry metadata only.
- **Scenario skills** each have a numbered class check with the exact sentence the agent should say when a stage cannot run, and an explicit ban on generic schemas. `large_file_upload_exfil` skips only the proxy sub-stages when no proxy is installed, and `dns_tunneling_c2` accepts the FortiGate DNS subsystem as its DNS source. Verification queries use the dataset name of the installed source.
- **Plugin reference agents and the `phantom-soc-v1` benchmark** allow-listed tool names no connector provides (for example `xsiam_execute_xql_query`, `phantom_list_scenarios`). They use real names now, and a test fails on any unknown name.

## [v1.0.2] — 2026-10-11 — *Security update*

**Security: the MCP tool endpoint on port 8080 was not authenticated (affects v1.0.0, v1.0.1 and every earlier build).** The embedded MCP server's JSON-RPC endpoint (`/api/v1/stream/mcp`) accepted requests with no credential at all, and Phantom publishes port 8080 on the host. Anyone who could reach that port could list and call all of the agent's tools: run queries through any configured XSIAM or Cortex instance, start and stop log workers, create scheduled jobs, install or upload connectors. The UI and agent API on port 3000, and every REST route on 8080, were already authenticated and were not affected.

- **What changed.** The endpoint now requires `Authorization: Bearer <MCP_TOKEN>` (what the agent itself uses) or an API key that holds the `tools:call` scope. Anything else gets 401 or 403 before a tool is reached.
- **API keys no longer reach beyond their scopes on port 8080.** The REST routes there accepted any valid key at any scope, so a key minted for one purpose, say `audit:read` for a SIEM poller, could also read instances and settings and create jobs. A key is now accepted only where its scope is named (`audit:read` for the audit log, `settings:read` / `settings:write` for settings, `approvals:resolve` for approvals, `tools:call` for the tool endpoint; `*` covers those and nothing more). Everything else on 8080 needs the internal token. The agent API on port 3000 is unchanged.
- **The approval-bypass header** is honoured only from the agent's own token; from an API key it is ignored.
- **If you cannot upgrade yet:** block port 8080 from everything but the host itself (a host firewall rule, or publish it as `127.0.0.1:8080:8080` in `docker-compose.yml`), and treat any key that was ever issued as potentially misused: revoke and re-issue it after upgrading.
- **Client note.** If you call the tool endpoint from your own MCP client, send the token as `Authorization: Bearer <MCP_TOKEN>`.

**Dependencies.** Clears every critical and high dependency alert that GitHub reported on the public repository (2 critical, 9 high, plus the medium and low ones).

**Fixed.**

- **`xlog` runs on current, patched libraries.** It was pinned to 2024-era versions of FastAPI, Starlette, python-multipart, h11 and anyio. It now runs FastAPI 0.143, Starlette 1.7, Pydantic 2, Strawberry GraphQL 0.333, python-multipart 0.0.32, h11 0.16 and anyio 4.14. Three requirements nothing used (`ariadne`, `fastapi-utils`, `fastapi-cli`) were removed because they held the old versions in place.
- **The agent's build tooling no longer carries a vulnerable `postcss`.** Next.js pins its own copy; an npm override now points every copy at the patched release. The audit of production dependencies reports 0 vulnerabilities. One dev-only package (`braces`, used by Tailwind and ESLint) is rated high but has no patched release anywhere and is not part of the shipped image.
- **The request after a failed chat no longer gets an empty 400.** The TLS proxy in front of the UI reused upstream connections, and a chat stream that ended with an error (for example before any model provider is configured) left a connection behind that the next request picked up and Next rejected. Each request now uses its own connection to the backend.
- **Settings refuse a value of the wrong type.** The settings API stored whatever it was given, so a number for a text setting or the text `"false"` for a yes/no setting was saved and then read back as the wrong type. A value must now have the same JSON type as the setting's default; a mismatch is reported in the response's `rejected` list and nothing is stored for that key.
- **`xlog` starts reliably on a fresh database.** Its server runs several processes, and on a brand-new database file they could collide on the first SQLite setup step, killing one worker at startup (the supervisor restarted it). The step now retries briefly while another process holds the lock.

**Docs.** `/help/architecture#authentication` (API keys on the two ports), `/help/user#api-keys` (the scope table, now enforced) and the scope text on `/api-keys`.

## [v1.0.1] — 2026-10-11 — *Fresh-install fixes*

Two bugs found by installing v1.0.0 from the public release on a clean host (both made the first log-generation request fail), one hardening of the password change, and a fix for bare tool names.

**Fixed.**

- **A fresh install now serves xlog over HTTPS from the first start.** On an empty install the TLS certificate was created too late: the agent wrote it, but the agent only starts after `xlog` is healthy, and `xlog` had already given up waiting and fallen back to plain HTTP. Every log-generation tool then failed with `[SSL] record layer failure`, and `/api/agent/health` reported `degraded`. A new one-shot step, `phantom_tls_init`, creates the certificate before any of them starts, and never overwrites a certificate you supplied. It appears as `Exited (0)` in `docker compose ps -a`. No action is needed on an existing install: the certificate is already there.
- **Guessing the password through the Change password form is now rate-limited.** The form checks your current password, but unlike sign-in it had no lockout, so a stolen session cookie could be used to guess the password. Five wrong current passwords in a minute now lock the form for 60 seconds (HTTP 429), counted per source address and per session, with a separate counter from sign-in. Sign-in's own lockout also now keys on the address the proxy saw, not on a header the client can set, and attempts are counted before the password check so parallel guesses cannot slip through.
- **A bare tool name works in direct tool calls.** `^run_xql_query query=...` in chat, or a bare name sent to `/api/agent/tool/call`, was refused as "ambiguous" even when only one connector provides the tool, because each tool is advertised under its namespaced name and its legacy flat alias. Those two names are now recognised as the same tool and the namespaced one is used. When two connectors provide a tool with the same name (for example Cortex XDR and XSIAM), you still have to say which one, as before.
- **Generating logs without a vendor schema works again.** Asking the agent for a worker without a data-source schema (the generic path) was always rejected with `Field 'durationSeconds' is not defined by type 'WorkerFakerInput'`. Workers that use a data source's schema were not affected. On the generic path a worker stops after `count` events; `duration_seconds`, `max_events` and `continuous` apply only with a data-source schema, and the tool result now says so.

**Docs.** `/help/architecture#tls-proxy` (new subsection, "Who creates the certificate, and boot order"), a note under `#stack`, and the rate-limit bullet under `#authentication`; `/help/user#authentication` and the change-password journey mention the lockout.

## [v1.0.0] — 2026-10-11 — *First public release*

Phantom is a continuous SOC simulation platform for defensive detection engineering. It generates synthetic security telemetry, runs MITRE ATT&CK scenarios end to end, and lets an AI agent orchestrate red and blue workflows against your own detection stack over MCP. Everything it produces is synthetic log data sent only to destinations you control.

This is the first public release, so there is no upgrade path from earlier builds. Install v1.0.0 fresh with the `phantom-installer` from the GitHub Release.

**What you get.**

- **A five-service Docker Compose stack.** `phantom-agent` (the Next.js operator UI with an embedded Python MCP server, one trust boundary), `xlog` (the synthetic-log generator), `caldera` (MITRE Caldera for red-team operations), `phantom-updater` (per-instance connector container lifecycle) and `phantom-browser` (headless Chromium for web research). The installer writes credentials and pins every image by digest.
- **An AI agent in chat.** Describe a goal in plain language and the agent chains MCP tools and skills to reach it, with live tool-call telemetry, saved sessions, memory, knowledge bases, scheduled jobs, tasks, and approval and personality controls for how much it asks before acting on external systems.
- **Synthetic log generation.** The `xlog` engine produces CEF, syslog, LEEF and JSON events with consistent identities, field-level control, throughput reporting and bounded simulation workers.
- **Nearly 300 data sources.** Each describes the shape of one vendor's logs as the Cortex parsing and modeling rules expect them, so events land in the right dataset and map to the data model. Edit, pin, upload or install your own from the marketplace.
- **Scenario-based MITRE ATT&CK telemetry.** Ready-made multi-stage scenarios, plus Caldera operations with bundled abilities and adversaries for the real-endpoint side.
- **Pluggable connectors, one container per instance.** Built in: `xlog`, `xsiam`, `caldera`, `cortex-content`, `cortex-docs`, `cortex-xdr`, `web`, `http-sender` and `wec-sender`. Install them from the marketplace, configure instances in the UI, or upload your own `connector.yaml`.
- **Log destinations.** Send to a syslog or CEF broker, an HTTP collector, Splunk HEC, a webhook, or a Cortex Cribl endpoint.
- **Detection validation.** Skills and tools to run XQL, read alerts, datasets and cases, and check that a synthetic scenario produced the detection you meant to test.
- **Secure by default.** TLS everywhere, an encrypted secret store, PBKDF2 operator login, scoped API keys, and a hard boundary that keeps credentials out of the agent's reach: provider keys, connector secrets and API keys are managed only by you in the UI, never by the agent, including inside a batched plan.
- **Observability.** Metrics, traces, logs, audit events, runtime events, cost, pipeline health and live activity, all in the UI.
- **Operations.** Backup and restore from Settings, a REST API with a downloadable OpenAPI spec, and in-product architecture and user guides with step-by-step user journeys.

**Capability acceptance criteria.** On a fresh install an operator can log in, add a model provider, install a connector, ask the agent to generate logs for a data source, and see the events arrive at their own collector.

**Docs.** `/help/architecture`, `/help/user`, `/help/journeys` and `/help/api` in the running UI.
